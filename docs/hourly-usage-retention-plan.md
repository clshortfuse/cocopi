# Hourly usage retention plan

## Goal

Keep the most recent 5,000 detailed Token Tracker rows, while preserving older local usage as UTC-hour aggregates in the same private JSON storage value. Backfill aggregates from retained rows as they are evicted. Rows already discarded cannot be recovered locally; remote account analytics remain separate and must not be added to local totals.

## Design

- Store hourly aggregates alongside detailed rows, grouped by UTC hour and the model, reasoning effort and workload dimensions required by existing analytics. Retain request counts, known/unknown usage counts, token totals, and sufficient timing sums and counts for existing averages. Do not preserve prompt content or session identifiers in rollups.
- Roll up only evicted rows. Detailed rows and rollups must be disjoint so analytics can combine them without double-counting. Backfill existing retained rows as they are evicted, not by duplicating all rows during migration.
- Version the stored JSON and migrate existing versions without losing rows. Preserve the existing serialized write queue and handle rows recorded while storage is loading. Include rows evicted during the startup merge in the rollups exactly once.
- Include rollups in aggregate usage windows, weekly-cycle and timeline totals, model series, and workload summaries. Keep session and individual-row views explicitly limited to detailed retained rows; aggregate data cannot reconstruct sessions.
- Use UTC hour boundaries for persisted buckets. For windows cutting through an archived hour, expose the hourly resolution and use a consistent, documented boundary policy rather than pretending the original request timestamps are known. Align timeline buckets with UTC hours to avoid splitting an aggregate or shifting it at daylight-saving transitions.
- Deleting an individual retained row or session removes those detailed records as today; it cannot subtract already-aggregated session usage. Make this limitation visible in the tracker. Clearing tracker history clears both detailed rows and rollups. Preserve unknown counters as unknown rather than fabricating zero usage.
- Bound storage growth by documenting a retention policy for hourly aggregates before implementation; do not silently impose a short window that recreates the 5,000-row problem. Keep account-wide remote analytics separate from local usage.

## Validation

Storage isolation: combined detailed rows and hourly aggregates use `cocopi.diagnostics.tokenTracker.v2`. When absent, migrate `cocopi.diagnostics.tokenTracker.v1` once, leaving that legacy value untouched. Once the new key exists, ignore legacy updates, including after clearing the new tracker. Usage generated by an older build is not merged back automatically. Hourly aggregates have no automatic expiration; explicit clear/delete behavior remains unchanged. Archived usage is attributed to the UTC hour start for partial-window calculations.

- Add offline tests for more than 5,000 rows, exact totals across eviction, UTC hour and daylight-saving boundaries, model/workload grouping, missing counters, clear and delete behavior, migration, restart, and concurrent startup recording.
- Verify analytics do not double-count detailed and rolled-up rows, and document any boundary-hour approximation in the UI.
- Run `npm run check`, `npm run lint`, and `npm test`; preserve unrelated changes and stage only files changed for this task.
